[기타 애로사항]

시연 시간이 문제다. 평소 설정은 하루 2회 분석이라 시연 중에 분석이 돌 리가 없고, 5분 모드로 바꿔도 이상 주입 → 5분마다 분석 × 2번 연속 → 확장 → 10분 뒤 검증까지 25분이 걸려서 발표 시간 안에 못 끝낸다. 시연 때만 1분 간격 모드로 바꾸고 검증 대기를 3분으로 줄였는데, 이렇게 줄여도 평소에 오탐이 안 나는지 리허설로 확인했다. [측정: 결과] 시연 8분 동안의 OpenAI 호출은 10번 남짓이라 비용은 문제없다.

발표장 인터넷이 걱정된다. 서울 API, OpenAI, Cloudflare 세 군데에 의존하고 있어서 인터넷이 불안하면 시연이 흔들린다. 각각 안 될 때 어떻게 할지 별지에 적어 뒀다.

구글 로그인은 승인된 도메인을 미리 등록해야 하는데 터널 주소가 매번 바뀌어서 시연에서는 일반 로그인만 보여주기로 했다.

별지 1. 연구 내용

1. CI/CD

방학 동안 테스트를 많이 썼는데 정작 자동으로 도는 곳이 없어서 GitHub Actions를 붙였다. 코드를 올릴 때마다 백엔드 테스트(MySQL 컨테이너를 띄워서), AI 서비스 테스트, 프론트엔드 타입 검사와 빌드, Docker 이미지 빌드가 돈다.

하나 더 넣은 게 있는데, docker-compose 확장 설정이 나중에 실수로 깨지는 걸 막는 검사다. 1회 보고에서 "수집은 한 대만" 구조를 만들었는데, 누가 backend 설정에서 스케줄러를 다시 켜거나 포트를 고정해 버리면 확장이 안 되면서도 겉으로는 티가 안 난다. 그래서 compose 파일을 파싱해서 이 조건이 깨지면 CI가 실패하게 했다.

버전 태그(v0.1.0, v0.2.0)를 붙이면 Docker 이미지가 GitHub 컨테이너 저장소에 올라가게 했다. 리눅스 amd64용으로만 만드는데, ARM까지 만들려면 에뮬레이션 때문에 빌드가 몇 배로 느려져서 배포 대상(리눅스 서버)에만 맞췄다. 맥에서는 이미지를 받지 않고 직접 빌드하면 된다.

2. 어느 주소에 올려도 되게 만든 것

외부에서 접속할 수 있게 하려고 처음 터널을 뚫어 봤을 때 화면은 뜨는데 데이터가 하나도 안 나왔다. 확인해 보니 프론트엔드가 빌드될 때 백엔드 주소가 localhost:8080으로 박혀 있어서, 외부에서 열면 브라우저가 자기 컴퓨터의 8080으로 요청을 보내고 있었다. 주소가 바뀔 때마다 프론트엔드를 다시 빌드해야 하는 구조였다.

프론트엔드를 서빙하는 nginx가 /api로 오는 요청을 백엔드로 넘겨주게 바꿔서, 브라우저 입장에서는 프론트엔드와 백엔드가 같은 주소가 되게 했다. 이러면 프론트엔드가 백엔드 주소를 알 필요가 없어서 어느 주소에 올려도 재빌드가 필요 없고, CORS 문제도 같이 없어진다.

고치는 김에 API 주소를 계산하는 코드가 파일 9개에 흩어져 있던 걸 한 파일로 모았다. 여기서 사소한 버그를 하나 만났는데, 기본값 처리를 ||로 하고 있어서 "빈 문자열 = 같은 주소"라는 설정을 무시하고 기본값으로 넘어가 버렸다. ??로 바꿨다.

터널로 실제 확인한 결과, 한 주소에서 화면 이동, 역 목록, 관리자 로그인과 관리자 API가 다 됐고, Elasticsearch와 Kibana는 밖에서 안 열리는 것도 확인했다.

3. 시연 준비

3.1 환경

노트북에서 확장 구성(backend 1대 + collector 1대 + nginx + DB + ELK + AI)으로 띄우고, Cloudflare 터널로 공개 주소를 만든다. 청중이 휴대폰으로 사용자 화면에 들어와 볼 수 있다. 호스트에서 워커를 실제 실행 모드로 켜 두어서 승인하면 진짜로 서버가 늘어나게 한다. 시뮬레이터는 발표 2주 전부터 돌려서 기준 데이터가 있는 상태로 시작한다.

별지 2. 문제점 및 해결

1. 외부에서 접속하면 데이터가 안 나오던 문제

별지 1의 2절. 프론트엔드에 백엔드 주소가 빌드 시점에 박혀 있어서 그랬다. nginx로 같은 주소에서 넘겨주게 바꿔서 해결했다. 터널을 처음 뚫어 보기 전까지는 몰랐던 문제라, 실제로 밖에서 접속해 보는 게 중요하다는 걸 느꼈다.

2. 테스트가 자동으로 안 돌던 문제

CI가 없어서 테스트를 써 놓고도 실제로 돌리는 건 각자 알아서였다. GitHub Actions를 붙여서 해결했다. 붙이고 나서 워커 테스트가 CI에서만 실패하는 게 하나 나왔는데, 워커가 파일 맨 위에서 Elasticsearch 라이브러리를 불러오고 있어서 라이브러리 설치 없이 도는 CI 단위 테스트에서 깨진 것이었다. 실제로 쓰는 함수 안으로 옮겼다.

3. 시연 시간 문제 [측정]

평소 설정(하루 2회)으로는 시연이 불가능하고, 5분 모드로도 25분이 걸려서 시연용 설정을 따로 뒀다(별지 1의 3.2). 줄인 설정에서 오탐이 늘지 않는지 리허설로 확인했다. [측정: 결과. 문제 있었으면 어떻게 조정했는지]

4. 비밀번호가 코드에 그대로 있던 것 [측정]

docker-compose.yml과 설정 파일에 DB 비밀번호(subway123, root)가 그대로 있고 저장소가 공개라서 외부 서버에 올리면 위험하다. .env로 옮기고 compose에서 참조하게 [측정: 바꿨다 / 아직].
