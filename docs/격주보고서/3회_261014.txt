──────────── ④ [진도상황 확인] 칸 ────────────

지난 보고에서 분석 주기를 하루 두 번에서 5분 간격 상시 관측으로 되돌렸고, 이번 기간에는 그 상태로 12일간 운영하며 결과를 확인했습니다. 시뮬레이터가 주입한 트래픽 급증 38회 중 24회를 탐지했습니다. 지난 기간에는 12회를 주입해 한 번도 탐지하지 못했으므로 가장 큰 과제가 해결되었습니다.

이어서 최종 발표를 위한 시연 리허설을 진행했습니다. 실제 서버에 평소의 약 10배 요청을 보내 급증을 만들고, 탐지부터 오탐 검증, 원인 진단, 확장 제안, 관리자 승인, 서버 2대로 확장, 효과 검증까지 전 과정이 이어지는 것을 확인했습니다. 급증 시작부터 검증 성공까지 약 9분이 걸려 발표 시간 안에 시연할 수 있습니다.

리허설에서 보완할 점이 두 가지 나와 바로 수정했고, 다시 리허설을 진행해 개선된 것을 확인했습니다.

일정은 하나 조정했습니다. 외부 서버 구동은 최종 발표에 꼭 필요하지 않아 11월로 옮기고, 발표는 노트북에서 시연할 예정입니다.

별지 1. 연구 내용

1. 이번 기간에 한 일

  · 상시 관측 확인 — 5분 간격 분석을 12일간 운영하고 급증 탐지 결과 집계
  · 시연 리허설 — 시연용 설정으로 자동 대응 전 과정을 실제로 실행하고 시간 측정
  · 리허설 보완 — 검증 패널 판단 기준과 서버 대수 집계를 수정하고 재확인
  · 일정 조정 — 외부 서버 구동을 11월로 이동

2. 5분 상시 관측 결과

지난 기간에는 하루 두 번, 각각 10분 구간만 분석했기 때문에 5~12분 동안 지속되는 급증과 겹칠 일이 거의 없었습니다. 정상일 때는 LLM을 호출하지 않도록 고친 덕분에 5분 간격으로 분석해도 비용이 들지 않게 되었고, 이번 기간에는 이 방식으로 운영했습니다.

  · 운영 기간: 9월 28일 ~ 10월 10일
  · 분석 실행: 약 2,800회 (지난 기간 12회)
  · 주입한 트래픽 급증: 38회
  · 탐지한 급증: 24회 (지난 기간 0회)
  · 급증 시작부터 탐지까지: 중앙값 6분 (최소 2분, 최대 14분)

놓친 급증 14회 중 12회는 새벽 2시~6시 사이에 발생했습니다. 새벽에는 평소 요청이 매우 적어, 5~9분짜리 급증이 30분 분석 구간의 평균에 묻히면서 통계 기준을 넘지 못했습니다. 분석 구간을 줄이면 개선될 것으로 보고 있습니다.

3. 시연 리허설

3.1 시연용 설정

평소 설정으로는 탐지부터 확장 후 검증까지 30분 가까이 걸려 발표 시간 안에 보여줄 수 없습니다. 그래서 시연 때만 주기를 줄여 진행했습니다.

  · 분석 주기: 5분 → 1분
  · 분석 구간: 30분 → 5분
  · 확장 후 검증 대기: 10분 → 3분
  · 확장 후 쿨다운: 15분 → 5분

주기를 줄이면 오탐이 늘지 않을까 걱정했는데, 정상 상태 분석 18회 동안 오탐은 한 번도 없었습니다.

3.2 리허설 결과

실제 백엔드에 평소의 약 10배 요청을 8분 동안 보냈습니다.

  · 0:00  급증 시작
  · 3:43  첫 감지 (한 번 더 감지되어야 확정)
  · 5:25  이상 확정 → 오탐 검증 → 원인 진단 → 확장 제안 생성
  · 5:56  관리자 승인
  · 6:03  서버 2대로 확장
  · 8:00  급증 종료
  · 9:04  검증 성공 (트래픽 신호 해소 확인)

승인 후 실제로 서버가 늘어나기까지 7초가 걸렸고, 확장 직후 요청이 두 서버에 188건, 152건으로 고르게 나뉘는 것을 nginx 로그로 확인했습니다.

원인 진단 에이전트는 엔드포인트별 집계, 시간 추이, 로그 샘플 등을 직접 조회하며 조사했습니다. 1차 리허설에서는 근거가 부족하자 원인을 지어내지 않고 "특정하지 못함"으로 마쳤고, 보완 후 진행한 2차 리허설에서는 4번 "확신 높음"으로 결론을 냈습니다.

별지 2. 문제점 및 해결

1. 컨테이너에 무료 모델 설정이 전달되지 않던 문제

지난 기간 무료 Gemini로 전환하면서 API 키만 컨테이너에 넘기고 주소와 모델명은 빠져 있었습니다. 통계 기반 탐지에는 영향이 없었지만 검증과 진단이 실행되지 못하고 있었습니다. 설정에 두 항목을 추가했고, 리허설에서 모든 호출이 정상 응답하는 것을 확인했습니다.

2. 검증 패널이 실제 급증을 오탐으로 판단한 문제

1차 리허설에서 검증 패널이 "CPU와 메모리 사용량이 낮으니 실제 부하가 아니다"라는 이유로 급증을 오탐으로 판단했습니다. 강등은 한 단계로 제한되어 있어 확장 제안은 정상적으로 나왔지만, 가벼운 요청은 많이 몰려도 CPU가 거의 오르지 않으므로 트래픽 급증은 자원 사용률과 별개로 판단해야 합니다.

리허설 수치를 그대로 평가 케이스로 추가해 같은 오판이 나오는 것을 먼저 확인했고, 오탐 판단 근거에서 이 경우를 제외하도록 프롬프트를 보완했습니다.

  · 판정 정확도: 10/11 (91%) → 11/11 (100%)
  · 심사관 일치율: 37/39 (95%) → 39/39 (100%)
  · 3회 반복 일관성: 13개 케이스 모두 동일
  · 리허설 판정 유지: 1차 3번 중 0번 → 2차 6번 중 5번

기존 오탐 케이스는 그대로 걸러져, 한쪽을 고치면서 다른 쪽이 나빠지지는 않았습니다.

3. 서버 대수가 실제보다 적게 집계되던 문제

1차 리허설에서 급증이 끝나고 정상이 이어졌는데도 서버 줄이기 제안이 늦게 나왔습니다. 확인해 보니 두 서버가 지표를 남기는 시각(매분 0초, 31초)과 분석 시각(매분 5초)이 어긋나, 분석 시점에는 서버가 1대로 집계되고 있었습니다.

서버 수를 "같은 분에 기록한 서버"가 아니라 "가장 최근 기록 기준 90초 안에 기록한 서버"로 세도록 수정했고, 같은 상황을 재현한 테스트를 추가해 통과를 확인했습니다. 서버 줄이기까지 이어지는 전 과정은 다음 리허설에서 함께 확인할 예정입니다.
