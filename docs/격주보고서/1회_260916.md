계획과 달라진 점은 백엔드를 API 서버와 수집 서버로 분리한 것이다. 자동 확장을 하려면 필요했다. AI 분석 주기는 원래대로 하루 2회(오전 8시, 오후 6시)를 유지했는데, 5분마다 돌리는 것도 만들어 보긴 했지만 OpenAI 호출 비용 때문에 쓰지 않기로 했다. 별지에 적었다.

다음 보고까지는 기능 추가 없이, 비어 있는 이상탐지 기준 데이터를 쌓는 것과 LLM 에이전트 부분을 정리하는 데 집중할 예정이다.

## [기타 애로사항]

이상탐지가 "과거 같은 시간대의 평소 수치"와 비교하는 방식이다 보니 과거 데이터가 어느 정도 쌓여 있어야 하는데, 실제 사용자가 없어서 데이터가 자연스럽게 쌓이지 않는다. 그래서 가짜 사용자 역할을 하는 스크립트를 만들어서 발표 전까지 계속 돌려야 하고, 그동안 노트북을 계속 켜 두어야 한다.

서울 열린데이터 API는 하루 호출 횟수 제한이 있어서 수집 주기를 마음대로 짧게 할 수 없다. 출퇴근 시간에는 1분, 낮에는 2분, 새벽에는 수집을 멈추는 식으로 조절하고 있다.

AI 분석이 한 번 돌 때마다 OpenAI를 최소 한 번은 호출한다(정상이어도 요약 문장을 받기 때문). 5분마다 돌리면 하루 288번이라 비용을 감당하기 어려워서 하루 2회로 제한하고 있다. 대신 그 시각 외에 생긴 문제는 놓친다는 한계가 있고, 이 때문에 생기는 문제 두 가지를 이번에 고쳤다(별지 2).

전체 시스템이 Elasticsearch, Kibana까지 포함하면 메모리를 4GB 넘게 써서 무료 서버에는 올릴 수가 없다. 발표 시연은 노트북에서 띄우고 임시 공개 주소를 만들어서 하는 쪽으로 생각하고 있다.

# 별지 1. 연구 내용

## 1. 작품 개요

서울 지하철 1호선 실시간 도착정보를 보여주는 웹 서비스를 만들고, 그 서비스가 잘 돌아가고 있는지를 로그를 기반으로 AI가 감시하는 시스템이다. 사용자는 역을 검색해서 도착정보를 보고 즐겨찾기를 등록할 수 있고, 관리자는 별도 대시보드에서 서비스 상태와 이상탐지 결과를 본다.

전체 흐름은 다음과 같다. 서울 열린데이터 API에서 도착정보를 주기적으로 가져와 MySQL에 저장하고, 이 과정에서 발생하는 로그(API 호출 결과, 요청량, 응답시간, CPU 사용률 등)를 Logstash를 거쳐 Elasticsearch에 쌓는다. Python으로 만든 AI 서비스가 이 로그를 주기적으로 읽어서 이상 여부를 판단하고 결과를 다시 Elasticsearch에 저장하면, Spring Boot 백엔드가 그걸 읽어서 React 관리자 화면에 보여준다.

| 구분 | 기술 |
|---|---|
| 프론트엔드 | React, TypeScript, Vite, Tailwind CSS |
| 백엔드 | Spring Boot, Spring Data JPA, MySQL |
| 로그 | Logstash, Elasticsearch, Kibana |
| AI | Python, LangGraph, OpenAI API |
| 실행 환경 | Docker Compose, nginx |

현재는 docker compose 명령 한 번으로 전체가 뜨고, 역 102개와 도착정보가 정상적으로 수집되며, 로그 적재와 AI 분석 실행까지 확인된 상태다.

## 2. 이상탐지 판정 방식을 다시 만든 이유

### 2.1 무엇이 문제였나

1학기에 만든 이상탐지는 "최근 30분 데이터를 과거 28일 같은 시간대의 평균과 비교해서, 1.5배를 넘으면 주의, 2배를 넘으면 위험"이라는 방식이었다. 말로는 그럴듯했는데, 방학 초에 정상 상태에서 테스트를 해 보니 이상 알람이 거의 항상 떠 있었다. 알람이 항상 떠 있으면 아무도 안 보게 되므로 이건 없는 것과 같다.

원인을 찾아보니 비교 자체가 잘못되어 있었다. 최근 30분 동안의 **최댓값**을 과거의 **평균**과 비교하고 있었다. 30분 동안 30개의 값이 있으면 그중 가장 큰 값은 당연히 평균보다 크다. 그러니까 정상 상태여도 "평균의 1.5배"는 거의 항상 넘는다. 값이 튀어서가 아니라 비교 방법 때문에 알람이 나고 있었던 것이다.

이것 말고도 몇 가지가 더 있었다.

- README에는 "z-score 2 이상이면 이상"이라고 적어 놨는데, 코드를 보니 z-score를 계산만 하고 판정에는 안 쓰고 있었다.
- "총 요청 수가 1000건 이상이면 트래픽 급증"이라는 절대 기준이 있었는데, 30분 동안 1000건이면 초당 0.5건 정도라 트래픽 급증이라고 할 수 없다. 이것도 항상 알람이 나는 원인 중 하나였다.
- 과거 데이터에서 "같은 시간대"를 고를 때 분석 실행 시각을 기준으로 하고 있어서, 8시에 실행하면 7시 30분~8시 데이터를 8시대 기준과 비교하게 됐다. 출퇴근 시간 경계에서 기준이 어긋난다.

### 2.2 어떻게 고쳤나

비교를 두 가지로 나눴다. 최근 30분의 **평균**은 과거의 **평균**과 비교하고, 최근 30분의 **최댓값**은 과거의 **상위 1% 값**과 비교한다. 평균끼리 비교할 때는 배수 조건(1.5배)과 z-score 조건(2 이상)을 둘 다 만족해야 이상으로 본다. 둘 중 하나만 쓰면 과거 데이터가 들쭉날쭉한 시간대에서 오탐이 나기 때문이다.

절대 기준은 총 요청 수가 아니라 초당 요청 수로 바꿨다. 분석 창 길이를 바꿔도 의미가 변하지 않도록 하기 위해서다.

분석 주기는 고민을 좀 했다. 하루 2회(오전 8시, 오후 6시)는 그 시각 앞뒤 30분만 보는 거라 나머지 시간에 생긴 문제는 모른다. 그래서 5분마다 돌리는 모드를 만들고, 5분마다 돌면 순간적으로 튄 값에 알람이 자주 날 수 있으니 두 번 연속 이상일 때만 확정하는 조건도 넣었다. 그런데 분석 한 번에 OpenAI를 한 번씩 부르기 때문에(정상이어도 요약 문장을 받는다) 5분마다면 하루 288번이라 비용이 감당이 안 됐다. 결국 운영은 하루 2회로 두고 5분 모드는 옵션으로만 남겼다.

이렇게 정하고 나니 "두 번 연속" 조건이 하루 2회 모드에서는 말이 안 된다는 걸 나중에 알았다. 직전 실행이 10시간 전이라 아침저녁 둘 다 이상이어야 확정되는 셈이고, 10분짜리 급증은 영원히 확정이 안 된다. 하루 2회 모드에서는 이 조건을 자동으로 끄게 하고, 오탐은 다른 방법(검증 패널, 다음 보고에서 설명)으로 거르기로 했다.

과거 데이터가 충분하지 않은 시간대(5건 미만)에는 비교를 하지 않고 절대 기준만 쓴다. 이 부분이 지금 데이터가 부족해서 실제로 자주 걸리는 경로인데, 애로사항에 적었다.

수정 후 테스트 코드를 29개 작성했다. 특히 "최댓값이 3배여도 평균이 평소와 같으면 정상"처럼 예전 방식에서 틀리게 판정하던 케이스를 넣어서 다시 돌아가지 않도록 했다.

### 2.3 LLM이 판정을 바꾸지 못하게 한 것

이상탐지 결과를 OpenAI에 보내서 요약과 조치 방안을 문장으로 받아오는 부분이 있다. 프롬프트에 "통계 결과를 따르라"고 써 놨는데, 실제로 돌려 보면 모델이 가끔 "정상"을 "주의"로 바꾸거나 이상 건수를 다르게 적어서 돌려줬다. 프롬프트로는 막을 수가 없어서 코드에서 막았다. 모델 응답에서 제목, 요약, 조치 방안 같은 문장만 가져오고, 상태·심각도·건수 같은 판정 값은 통계 결과로 덮어쓰게 했다. 모델 호출이 실패하면 통계 결과만으로 저장한다.

## 3. 서버를 여러 대로 늘릴 수 있게 만든 것

자동 대응에서 하려는 일이 "트래픽이 몰리면 API 서버를 한 대 더 띄우는 것"이라서, 먼저 서버가 두 대 이상이어도 문제가 없어야 했다. 실제로 두 대를 띄워 보니 몇 가지가 깨졌다.

가장 큰 문제는 도착정보 수집이었다. 수집 스케줄러가 두 대에서 동시에 도니까 서울 API를 두 배로 호출해서 하루 한도를 빨리 써 버리고, 더 심각하게는 저장 방식이 "기존 데이터를 전부 지우고 새로 넣기"라서 한 대가 지우는 사이에 다른 대가 넣은 데이터가 사라져 사용자에게 빈 화면이 나가는 순간이 생겼다. 그래서 수집은 한 대만 하도록 설정으로 분리했다. API 요청을 받는 서버(backend)는 여러 대, 수집만 하는 서버(collector)는 한 대다.

두 번째로, 로그에 "서버 몇 대가 돌고 있는지"를 남기는 값이 1로 고정되어 있었다. 서버를 늘려도 AI 쪽에서는 계속 한 대로 보였다. 각 서버가 자기 호스트명을 로그에 남기게 하고, AI가 최근 1분 로그에서 서로 다른 호스트명 개수를 세서 판단하도록 바꿨다. 방금 껐거나 재시작한 서버가 30분 창 안에 남아 있어서 더 많이 세는 문제도 있어서 최근 1분만 보게 했다.

세 번째는 nginx 설정이다. docker compose의 --scale 옵션으로 서버를 늘리면 nginx가 처음 뜰 때 잡은 IP 하나로만 보내고 새로 뜬 서버로는 안 보냈다. nginx가 요청할 때마다 Docker DNS에서 주소를 다시 찾도록 설정을 바꿔서 해결했다.

이 밖에 스케줄러의 실행 횟수 카운터가 스레드 안전하지 않은 int였던 것을 AtomicLong으로 바꿨고, 헬스체크 엔드포인트를 추가해서 서버가 준비된 뒤에 요청을 받도록 했다.

확인은 backend 두 대를 띄워서 했다. 요청이 두 대에 거의 반반씩 나뉘어 갔고, 수집은 collector 한 대만 실행했으며 backend 쪽 수집 횟수는 0이었다.

## 4. 자동 대응 기능

### 4.1 구조

이상이 확정되면 AI 서비스가 "backend를 1대에서 2대로 늘리자"는 제안을 만들어 저장한다. 관리자가 대시보드에서 승인하면, 노트북(호스트)에서 따로 돌고 있는 워커 프로그램이 실제로 docker compose --scale 명령을 실행한다. 10분 뒤에 워커가 분석 결과를 다시 확인해서 이상이 사라졌으면 성공으로, 남아 있으면 실패로 기록하고 원래 대수로 되돌리는 제안을 만든다. 이때 "확장한 뒤에 나온" 분석 결과여야 하므로, 아직 새 결과가 없으면 워커가 분석을 한 번 강제로 돌린 다음 판정한다.

AI 서비스가 직접 docker 명령을 실행하지 않고 워커를 따로 둔 이유는 권한 때문이다. 컨테이너 안에서 docker 명령을 쓰려면 Docker 소켓을 마운트해야 하는데, 이건 사실상 호스트의 관리자 권한을 주는 것이라 AI 서비스에는 주지 않는 게 맞다고 봤다. 그래서 제안(AI), 승인(백엔드 API), 실행(호스트 워커)을 분리했다.

기본은 관리자가 승인해야 실행되는 방식이고, 자동 승인은 설정으로 켤 수 있지만 기본은 꺼 두었다.

### 4.2 안전장치

오탐이 한 번 나서 서버를 계속 늘리기만 하면 안 되기 때문에 제한을 몇 개 뒀다.

- 최대 4대까지만 늘린다. 4대에서도 이상이 계속되면 자동으로 더 늘리지 않고 "사람이 확인 필요"로 기록한다.
- 확장 직후 15분 동안은 새 제안을 만들지 않는다. 늘린 직후에는 지표가 안정될 시간이 필요하다.
- 아직 처리 안 된 제안이 있으면 새 제안을 만들지 않는다.
- 승인을 안 하고 60분이 지나면 제안이 만료된다. 한참 뒤에 승인해서 엉뚱한 시점에 확장되는 걸 막기 위해서다.
- 트래픽, CPU/메모리, 응답시간 이상일 때만 확장을 제안한다. 수집 스케줄러 실패나 서울 API 장애는 서버를 늘려도 해결이 안 되니까 제안하지 않는다.
- 정상 판정이 6번 연속 이어지면(하루 2회 기준 3일) 반대로 줄이자는 제안을 만든다.

되돌리기(롤백)를 만들 때 롤백이 또 실패하면 롤백의 롤백을 만드는 식으로 무한히 왕복할 수 있어서, 롤백은 한 번만 만들고 그 뒤에는 사람에게 넘긴다.

### 4.3 확인

전체 흐름을 실제로 한 번 돌려 봤다. 트래픽 급증 로그를 넣고 → 제안 생성 → 대시보드에서 승인 → 워커가 backend를 2대로 늘림 → 10분 뒤 검증에서 실패 판정(테스트용 로그라 이상이 안 사라짐) → 롤백 제안 생성 → 롤백 실행으로 1대 복귀까지 됐다. 이 과정에서 제안이 정확히 2건(확장 1, 롤백 1)만 생긴 것을 확인해서 무한 반복은 없었다.

# 별지 2. 문제점 및 해결

## 1. 이상탐지 알람이 항상 떠 있던 문제

별지 1의 2절에 자세히 적었다. 정리하면, 최근 데이터의 최댓값을 과거 평균과 비교하고 있어서 정상 상태에서도 알람이 났고, 문서에 적힌 z-score 기준은 코드에 없었으며, 총 요청 수 절대 기준은 너무 낮았다. 비교 방식을 평균은 평균끼리, 최댓값은 상위 1%끼리로 나누고, z-score를 실제 판정에 넣고, 절대 기준을 초당 요청 수로 바꿔서 해결했다.

이걸 찾는 데 시간이 꽤 걸렸다. 처음에는 임계값이 너무 낮은 줄 알고 숫자만 올려 봤는데 여전히 알람이 났고, 로그를 한참 들여다본 뒤에야 비교 대상 자체가 잘못됐다는 걸 알았다.

## 2. 하행 도착정보가 계속 덜 들어오던 문제

서울 API를 여러 페이지로 나눠 호출하는데 하행 3페이지가 계속 실패하고 있었다. 로그에는 인증 실패로 나왔다. 확인해 보니 .env 파일에는 보조 키를 SUBWAY_API_KEY_2라고 적어 놨는데 코드에서는 SUBWAY_API_KEY_SECONDARY를 읽고 있었고, docker-compose에는 이 변수를 아예 넘기지 않고 있었다. 그래서 보조 키가 항상 기본값 "sample"로 나가고 있었다. 이름을 맞추고 compose에 추가하니 976건이 정상으로 들어왔다. 1학기 때부터 있던 문제였는데 그동안 상행만 보고 있어서 몰랐다.

## 3. 관리자 페이지에 로그인이 안 되던 문제

관리자 계정이 환경변수(ADMIN_EMAIL, ADMIN_PASSWORD)로 생성되는데 .env.example에 이 항목이 빠져 있어서 새로 세팅하면 계정이 안 만들어졌다. 예시 파일에 추가했다.

## 4. 서버를 두 대 띄웠을 때 생긴 문제들

별지 1의 3절에 적었다. 수집이 두 대에서 동시에 돌아서 데이터가 사라지는 문제, 서버 대수가 항상 1로 보이는 문제, nginx가 새 서버로 요청을 안 보내는 문제 세 가지였다. 첫 번째가 제일 찾기 어려웠는데, 화면에서 도착정보가 몇 초씩 비었다가 다시 나타나는 걸 보고 로그를 따라가 보니 두 서버가 번갈아 가며 서로 데이터를 지우고 있었다.

## 5. 자동 대응을 만들면서 고민한 것

문제라기보다 설계할 때 결정해야 했던 것들이다.

AI 서비스에 docker 실행 권한을 줄지 말지가 제일 컸다. 주면 구조가 간단해지는데, 컨테이너에 Docker 소켓을 넘기는 건 사실상 호스트 전체 권한이라 위험하다고 판단해서 실행은 호스트에서 따로 도는 워커에 맡겼다. 대신 워커를 별도로 켜야 해서 시연 때 잊지 말아야 할 것이 하나 늘었다.

되돌리기(롤백)를 자동으로 할지도 고민했다. 확장했는데 효과가 없으면 되돌리는 게 맞는데, 되돌린 것도 실패하면 어떻게 할지가 문제였다. 롤백은 한 번만 하고 그 뒤에는 사람에게 넘기는 것으로 정했다.

## 6. 하루 2회로 돌리면서 생긴 문제 두 가지

9월에 서버를 다시 띄우고 점검하다가 찾았다. 둘 다 5분마다 돌릴 때는 안 드러나던 것이다.

첫 번째는 위에 적은 "두 번 연속" 조건이다. 하루 2회 모드에서는 자동으로 끄게 고쳤다.

두 번째가 더 심각했는데, 확장 후 검증이 항상 실패하게 되어 있었다. 워커가 10분 뒤에 "가장 최근 분석 결과"를 보고 판정하는데, 하루 2회 모드에서는 10분 뒤에도 가장 최근 결과가 여전히 확장을 일으킨 바로 그 결과다. 당연히 이상이 남아 있으니 실패 → 롤백이 된다. 즉 자동 확장이 무조건 되돌려지는 구조였다. 5분마다 돌릴 때는 10분 안에 새 결과가 생겨서 몰랐다. 검증할 때 "확장 이후에 생긴 결과"인지 확인하고, 없으면 분석을 한 번 강제로 돌리도록 워커를 고쳤다. 고친 뒤에 실제로 확장된 것으로 가정한 작업을 넣고 돌려서, 워커가 분석을 새로 돌리고(약 6초) 그 결과로 성공 판정을 내리는 것까지 확인했다.

## 7. 아직 해결 안 된 것

- **과거 데이터 부족.** Elasticsearch에 5~7월 로그는 있지만 9월 로그는 거의 없어서, 지금 상태로 시연하면 "과거와 비교"가 아니라 절대 기준으로만 판정된다. 트래픽 시뮬레이터를 발표 전 최소 2주 동안 계속 돌려야 한다. 다음 보고에서 결과를 적을 예정이다.
- **AI 서비스가 Elasticsearch보다 먼저 떠서 첫 분석이 실패한다.** 9월에 서버를 다시 띄우면서 발견했다. compose에서 시작 순서만 지정되어 있고 "준비될 때까지 기다리기"가 없어서 그렇다. 수정은 간단한데 아직 안 했다.
- **서버를 줄이는(scale_in) 경로는 실제로 돌려 보지 못했다.** 정상 판정이 6번 이어져야 해서(하루 2회면 3일) 테스트 코드로만 확인했다. 리허설 때는 분석을 수동으로 여러 번 돌려서 확인할 예정이다.
- **하루 2회 모드는 그 시각 앞뒤 30분 밖에서 생긴 문제를 못 본다.** 비용 때문에 감수하기로 한 한계다. 정상일 때는 OpenAI를 부르지 않게 고치면 5분마다 돌려도 비용이 거의 안 들 텐데, 이건 시간이 되면 해 볼 생각이다.
