별지 1. 연구 내용

1. LLM 에이전트가 하는 일

지난 보고에서 이상탐지 판정은 전부 통계 규칙이 하고 LLM은 문장만 쓴다고 적었다. 이번에 정리하는 부분은 이상이 "확정된 뒤에" 돌아가는 세 가지다.

AI 서비스는 하루 2회(오전 8시, 오후 6시) 돌면서 먼저 통계로 판정을 하고, 그 결과를 OpenAI에 보내서 요약 문장을 받는다(이건 정상이어도 한 번 부른다). 정상이면 여기서 저장하고 끝난다. 이상이면 먼저 오탐인지 검증하고, 오탐이 아니면 원인을 조사하고, 그 다음에 저장하고 대응 제안을 만든다. 그러니까 평소에는 하루 2번, 이상이 있는 날에만 검증(3번)과 진단(최대 6번) 호출이 더 붙는다.

2. 원인 진단 에이전트

통계 규칙은 "무엇이 이상한가"(예: 트래픽이 평소의 3배)는 알려주지만 "왜"는 모른다. 이 부분을 LLM에게 맡겼다.

방식은 LLM에게 로그를 조회하는 도구 4개를 주고 스스로 조사하게 하는 것이다. 도구는 필드별로 묶어서 세기(어느 엔드포인트에 요청이 몰렸는지), 시간대별 추이 보기, 조건에 맞는 로그 원문 몇 개 꺼내 보기, 특정 필드 값 분포 보기다. LLM이 가설을 세우고 도구를 하나 골라 호출하면 결과를 다시 넣어 주고, 이걸 최대 6번 반복한 뒤 근본 원인과 확신도, 근거를 JSON으로 내놓게 했다.

지어내는 걸 막기 위해 도구 결과에 없는 숫자나 원인은 쓰지 말라고 프롬프트에 넣었고, 6번 안에 원인을 못 찾으면 "확신 낮음"으로 끝내게 했다. 이 결과는 설명용이고 판정이나 대응에는 영향을 주지 않는다.

실제로 OpenAI를 붙여서 돌려 보니 트래픽 급증 케이스에서 오류 코드별 집계 → 엔드포인트별 집계 → 로그 샘플 → 시간 추이 순서로 4번 조사하고 원인을 냈다. 테스트 코드에서 정해 둔 순서와 달라서 실제로 스스로 고르고 있다는 건 확인이 됐다.

3. 오탐 검증 패널

통계상으로는 이상이 맞는데 실제로는 신경 쓸 필요 없는 경우가 있다. 서버를 막 재시작해서 첫 몇 초 응답이 느린 경우, 딱 한 번 튀고 바로 돌아온 경우, 과거 데이터가 너무 적어서 비교가 의미 없는 경우 같은 것들이다.

이걸 거르려고 같은 데이터를 세 가지 다른 관점으로 보게 했다. 하나는 "이거 재시작 때문 아니야?"라고 의심하는 역할, 하나는 "잠깐 튄 거 아니야?"라고 의심하는 역할, 하나는 "근거가 충분해?"라고 따지는 역할이다. 셋은 서로 결과를 못 보고 각자 판정하고, 둘 이상이 오탐이라고 하면 심각도를 한 단계 낮춘다. 지난 보고에서 하루 2회 모드에서는 "두 번 연속" 조건을 껐다고 했는데, 그 역할을 이 패널이 대신한다.

여기서 중요한 건 낮추기만 하고 올리지는 못한다는 것이다. 통계가 정상이라고 한 걸 LLM이 이상으로 바꾸는 일은 없게 했다. 판정 권한은 계속 통계 쪽에 있다.

4. 재계획

확장을 했는데 10분 뒤에도 이상이 남아 있으면 지난 보고에서는 그냥 되돌렸다. 이번에 진단 결과를 참고해서 "한 대 더 늘릴지, 되돌릴지"를 나누게 했다. CPU가 여전히 높고 아직 상한(4대)에 안 닿았고 진단에서 "서버 늘려도 소용없는 원인"(외부 API 장애, 느린 쿼리 등)을 지목하지 않았으면 한 대 더 늘리고, 그 외에는 되돌린다.

이 결정 자체는 LLM이 하지 않고 코드로 정해 놨다. 진단 결과는 참고만 한다. 서버를 늘리고 줄이는 결정을 LLM에게 맡기는 건 아직 위험하다고 봤다.

5. 관리자 화면

진단 과정(어떤 도구를 왜 불렀고 뭘 봤는지)을 순서대로 보여주는 타임라인과, 검증 패널 세 명의 판정과 이유를 나란히 보여주는 화면을 관리자 대시보드에 추가했다. 백엔드에 API 두 개를 추가했다.

6. 평가

6.1 검증 패널

진짜 이상 / 오탐 / 애매한 경우를 섞어서 케이스 12개를 만들고, 판정이 맞았는지, 세 심사관이 얼마나 일치했는지, 같은 케이스를 반복해도 같은 답을 내는지를 봤다.

처음 돌렸을 때 진짜 이상 두 개를 오탐이라고 낮춰 버리는 문제가 나왔다. 이유를 보니 심사관이 "서버가 한 대뿐이라 근거가 약하다", "과거 데이터가 40건이라 적다"는 이유를 대고 있었다. 한 대인 건 우리 환경에서 당연한 거고 40건은 충분한 양인데 모델이 이걸 근거 부족으로 본 것이다. 오탐 판정에 쓸 수 있는 이유를 프롬프트에서 제한하고 나니 12개 다 맞았고, 심사관 일치율도 61%에서 92%로 올랐다.

6.2 진단 에이전트

원인이 분명한 케이스, 원인이 두 개인 케이스, 원인이 불분명한 케이스, 로그가 거의 없는 케이스로 8개를 만들고 LLM에게 채점을 시켰다. 원인이 분명한 쪽은 90% 이상 맞췄는데, 원인이 불분명한 케이스에서 "모르겠다"고 해야 할 걸 억지로 원인을 만들어 내는 문제가 있었다(75%).

이걸 고치려고 "확신하는지" 여부를 따로 답하게 해 봤는데, 이번엔 원인이 분명한 케이스까지 "모르겠다"고 하기 시작했다. 한쪽을 고치면 다른 쪽이 나빠져서 원래대로 되돌렸다. 쓰고 있는 모델(gpt-4o-mini)이 "내가 지금 확신하는가"를 판단하는 데 약한 것 같다. 진단은 참고용 설명이라 판정에는 영향이 없으니 일단 알려진 한계로 두기로 했다.

7. 안정성 관련 수정

워커가 멈추면 전체가 멈추던 문제. 워커가 확장 실행 중에 죽으면 그 작업이 "실행 중" 상태로 영원히 남는다. 그런데 "처리 안 된 작업이 있으면 새 제안 안 함" 규칙 때문에 이후 제안이 전부 막혔다. 15분 넘게 실행 중인 작업은 실패로 정리하는 로직을 넣었다.

오류 응답에 내부 정보가 나가던 문제. 백엔드에서 예외가 나면 스택트레이스가 그대로 응답에 나가고 있었다. 공통 예외 처리를 붙여서 정해진 형식의 오류 메시지만 나가게 했다.

테스트. 백엔드에 관리자 API, 대응 API, 인증 쪽 테스트 23개를 추가해서 총 38개가 됐다. AI 서비스는 102개다. 둘 다 GitHub에 올릴 때마다 자동으로 돈다.

8. 기준 데이터 축적 결과 [측정]

실제 사용자가 없어서 비어 있던 트래픽·응답시간·CPU 기준 데이터를 시뮬레이터로 채웠다. Elasticsearch에 가짜 로그를 넣는 게 아니라 실제 백엔드에 요청을 보내서, 백엔드가 진짜로 집계한 값이 로그로 남게 했다. 출퇴근 시간에 요청을 많이 보내고 새벽에는 줄이는 식으로 하루 패턴을 흉내 냈고, 평균 8시간에 한 번씩 5~12분 동안 요청을 10배로 늘리는 "이상 상황"도 섞었다.

• 돌린 기간: 9/[측정] ~ 9/[측정], 중간에 멈춘 횟수 [측정]
• 시간대별(24시간 × 평일/주말) 데이터 개수: 최소 [측정], 평균 [측정]
• 5건 미만이라 비교 못 하는 시간대: [측정]개 (새벽 1~5시는 수집 자체를 안 해서 원래 비어 있음)
• 시뮬레이터가 넣은 급증 [측정]번 중 분석 시각(8시, 18시) 앞뒤 30분에 걸린 것 [측정]번 → 이상 확정 [측정]번, 검증 패널이 오탐으로 낮춘 것 [측정]번, 확장 제안까지 간 것 [측정]번
• 분석 시각에 안 걸린 급증은 당연히 못 잡는다. 이건 하루 2회 모드의 한계라 따로 [측정]번을 골라 분석을 수동으로 돌려서 잡히는지 확인했다.

별지 2. 문제점 및 해결

1. 검증 패널이 진짜 이상을 오탐으로 낮추던 문제

별지 1의 6.1절에 적었다. 심사관 역할의 LLM이 "서버 한 대", "데이터 40건"을 근거 부족으로 잘못 보고 있었다. 오탐이라고 판단할 수 있는 이유를 프롬프트에서 명시적으로 제한해서 해결했다. 평가 케이스를 안 만들었으면 못 찾았을 문제라, 평가를 먼저 만드는 게 맞다는 걸 느꼈다.

2. 진단 에이전트가 원인을 지어내는 문제 (미해결)

별지 1의 6.2절. 고치려다 반대쪽이 나빠져서 원래대로 되돌렸다. 모델을 바꾸면 나아질 수도 있는데 비용 문제가 있어서 일단 두기로 했다. 진단은 설명용이라 판정에는 영향이 없다.

3. 워커가 죽으면 이후 제안이 전부 막히던 문제

별지 1의 7절. 실행 중 상태로 남은 작업을 시간이 지나면 실패로 정리하게 해서 해결했다. 이건 테스트하다가 워커를 강제 종료했을 때 발견했다.

4. 9월 초 점검에서 발견한 것들 [측정: 해결했으면 체크]

방학 끝나고 서버를 다시 띄웠을 때 나온 문제들이다.

□ AI 서비스가 Elasticsearch보다 먼저 떠서 첫 분석이 실패했다. compose에 "Elasticsearch가 준비될 때까지 기다리기" 조건을 추가했다.
□ 사용자가 응답을 받다가 연결을 끊으면(브라우저 닫기 등) 서버 오류로 로그가 남고 있었다. 오류율 계산에 들어가면 안 되는 거라 따로 분류했다.

5. 아직 해결 안 된 것

• 서버 줄이기(scale_in)는 실제로 아직 못 돌려 봤다. 리허설 때 확인 예정.
• docker-compose.yml에 DB 비밀번호가 그대로 적혀 있고 GitHub에 공개되어 있다. 외부 서버에 올리기 전에 바꿔야 한다.
• 구글 로그인이 임시 주소에서는 안 된다(승인된 도메인을 미리 등록해야 하는데 주소가 매번 바뀜). 시연은 일반 로그인으로 할 예정.
• 상시 서버가 없다. 전시회(11/9) 때 어떻게 할지 정해야 한다.
