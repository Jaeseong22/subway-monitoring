2. LLM 에이전트가 하는 일

2.1 전체 흐름

AI 서비스는 주기적으로 깨어나 통계 규칙으로 먼저 판정한다. 정상이면 결과만 저장하고 끝난다. 이상이면 오탐인지 검증하고, 오탐이 아니면 원인을 조사하고, 그 다음에 저장하고 대응을 제안한다.

지표 수집 → 통계 판정 → (정상) 저장
지표 수집 → 통계 판정 → (이상) 오탐 검증 → (오탐) 강등 후 저장
지표 수집 → 통계 판정 → (이상) 오탐 검증 → (진짜) 원인 진단 → 저장 → 대응 제안

정상일 때는 LLM을 한 번도 부르지 않는다. 처음에는 정상이어도 요약 문장을 받으려고 매번 호출했는데, 판정과 수치는 어차피 통계 결과가 강제하고 정상 상태의 설명("특이 이상 없음")은 통계 쪽에서 이미 만들어 두기 때문에 얻는 것이 없었다. 이 호출이 비용의 대부분이었고, 이것 때문에 지난 보고에서는 분석 주기를 하루 두 번으로 줄여야 했다. 생략하도록 고친 뒤로는 5분 간격으로 돌려도 정상인 날은 비용이 0이 된다.

2.2 원인 진단 에이전트

통계 규칙은 "무엇이 이상한가"(예: 트래픽이 평소의 3배)는 알려주지만 "왜"는 모른다. 이 부분을 LLM에게 맡겼다.

LLM에게 로그를 조회하는 도구 네 개를 주고 스스로 조사하게 한다.

  · breakdown_by — 필드별(엔드포인트, 오류코드, 인스턴스 등) 집계
  · time_histogram — 5분 단위 시간 추이
  · sample_events — 조건에 맞는 로그 원문 샘플
  · field_values — 특정 필드의 값 분포

LLM이 가설을 세우고 도구를 하나 골라 호출하면 결과를 다시 넣어 주고, 이걸 최대 6번 반복한 뒤 근본 원인·확신도·근거를 JSON으로 내놓게 했다. 도구 결과에 없는 숫자나 원인은 쓰지 말라고 프롬프트로 강제했고, 6번 안에 못 찾으면 "확신 낮음"으로 끝내게 했다. 이 결과는 설명용이며 판정이나 대응에는 영향을 주지 않는다.

실제로 돌려 보면 케이스마다 조사 순서가 다르다. 외부 API 지연 케이스에서는 오류코드별 집계 → 엔드포인트별 집계 → 로그 샘플 순으로 3스텝, 스케줄러 실패 케이스에서는 4스텝을 썼다. 테스트 코드에 정해 둔 순서와 달라서, 실제로 스스로 고르고 있다는 것이 확인된다.

2.3 오탐 검증 패널

통계상으로는 이상이 맞는데 실제로는 신경 쓸 필요 없는 경우가 있다. 서버를 막 재시작해 첫 몇 초 응답이 느린 경우, 한 번 튀고 바로 돌아온 경우, 과거 데이터가 적어 비교가 의미 없는 경우 같은 것들이다.

같은 데이터를 세 가지 다른 관점으로 보게 했다. 하나는 "재시작 때문 아닌가"를 의심하고, 하나는 "잠깐 튄 것 아닌가"를 의심하고, 하나는 "근거가 충분한가"를 따진다. 셋은 서로의 결과를 보지 못한 채 각자 판정하고, 둘 이상이 오탐이라고 하면 심각도를 한 단계 낮춘다.

중요한 것은 낮추기만 하고 올리지는 못한다는 점이다. 통계가 정상이라고 한 것을 LLM이 이상으로 바꾸는 일은 없다. 판정 권한은 계속 통계 쪽에 있고, 패널은 거르는 역할만 한다.

2.4 재계획

확장을 했는데 검증 시점에도 이상이 남아 있으면, 지난 보고에서는 무조건 되돌렸다. 이번에 진단 결과를 입력으로 받아 "한 대 더 늘릴지, 되돌릴지"를 나누게 했다. 자원이 여전히 포화이고 상한(4대)에 닿지 않았고 진단이 "서버를 늘려도 소용없는 원인"(외부 API 장애, 느린 쿼리 등)을 지목하지 않았으면 한 대 더 늘리고, 그 외에는 되돌린다.

이 결정 자체는 LLM이 아니라 코드가 한다. 진단 결과는 근거로만 쓴다. 서버를 늘리고 줄이는 인프라 결정을 LLM에게 맡기는 것은 아직 위험하다고 판단했다.

2.5 대시보드 노출

진단 과정(어떤 도구를 왜 불렀고 무엇을 봤는지)을 순서대로 보여주는 타임라인과, 검증 심사관 세 명의 판정과 이유를 나란히 보여주는 화면을 관리자 대시보드에 추가했다. 백엔드에 조회 API 두 개를 추가했다.

3. 평가 체계

"에이전트가 잘 돈다"는 직감으로는 아무것도 보장할 수 없어서, 케이스와 채점표를 만들었다.

3.1 검증 패널 평가

진짜 이상 5개, 오탐 5개, 애매한 경계 2개로 12케이스를 만들고 네 가지를 봤다. 판정이 맞았는가, 심사관 셋이 얼마나 일치했는가, 반복해도 같은 답이 나오는가, 근거가 타당한가.

처음 돌렸을 때 진짜 이상 두 개를 오탐이라고 낮춰 버렸다. 근거를 뽑아 보니 심사관이 "서버가 한 대뿐이라 신뢰할 수 없다", "과거 데이터가 40건이라 적다"는 이유를 대고 있었다. 서버가 한 대인 것은 우리 환경에서 당연한 것이고 40건은 충분한 양인데 모델이 이것을 근거 부족으로 본 것이다. 오탐이라고 판단할 수 있는 이유를 프롬프트에서 제한하고 나니 12개 모두 정확해졌다.

  · 판정 정확도: 8/10(80%)에서 10/10(100%)으로
  · 진짜 이상을 놓친 건수: 2건에서 0건으로
  · 심사관 일치율: 61%에서 92%로
  · 반복 일관성: 측정 안 했다가 12회 반복 모두 동일

진짜 이상을 놓치는 것은 오탐을 남기는 것보다 위험하다. 평가를 안 만들었으면 못 찾았을 결함이다.

3.2 진단 에이전트 평가

원인이 분명한 케이스, 원인이 둘인 케이스, 원인이 불분명한 케이스, 로그가 거의 없는 케이스로 8개를 만들고 별도 LLM에게 채점을 시켰다.

  · 근본원인 정확성 11/12 (92%)
  · 도구 활용 8/8 (100%)
  · 결론 적절성 6/8 (75%)
  · 조사 효율 14/16 (88%)

원인이 분명한 쪽은 잘 진단하는데, 원인이 불분명한 케이스에서 "모르겠다"고 해야 할 것을 억지로 원인을 만들어 내는 문제가 있었다.

고치려고 "확신하는지"를 따로 답하게 해 봤더니, 이번엔 원인이 분명한 케이스까지 "모르겠다"고 하기 시작했다. 한쪽을 고치면 다른 쪽이 나빠져서 원래대로 되돌렸다. 검증 패널처럼 단순히 분류하는 일은 프롬프트로 고쳐졌지만, 진단처럼 여러 단계를 돌며 스스로 확신 여부를 판단해야 하는 일은 프롬프트로 쉽게 고쳐지지 않는다.

4. 무료 모델로 전환

4.1 왜 했나

지금까지 OpenAI 유료 API를 썼는데, 발표 전까지 시스템을 계속 켜 두어야 하는 상황에서 호출 비용이 부담이었다. 무료로 쓸 수 있는 Google Gemini API가 있어서, 성능이 크게 떨어지지 않는다면 바꾸는 것이 맞다고 판단했다.

다만 "비슷할 것 같다"는 느낌만으로 바꾸면 안 되고, 이미 만들어 둔 평가 셋이 있으니 숫자로 확인하기로 했다. 코드는 OpenAI 호환 방식으로 호출하도록 되어 있어서 환경변수 세 개(주소, 키, 모델명)만 바꾸면 공급자를 교체할 수 있다.

4.2 결과

같은 평가 셋을 두 모델로 돌린 결과는 다음과 같다.

왼쪽이 유료 gpt-4o-mini, 오른쪽이 무료 gemini-3.1-flash-lite다.

  · 검증 판정 정확도: 100% / 100%
  · 검증 심사관 일치율: 92% / 100%
  · 진단 근본원인 정확성: 92% / 100%
  · 진단 결론 적절성: 75% / 88%
  · 진단 조사 효율: 88% / 81%

네 축 중 셋에서 무료 모델이 더 좋고, 조사 효율만 조금 낮다(원인을 찾기까지 도구를 더 많이 쓴다). 특히 3.2에서 프롬프트로 고치지 못하고 한계로 남겨 두었던 억지 결론 2건 중 하나가 모델을 바꾸니 그냥 해결됐다. 프롬프트로 풀리지 않던 문제가 모델 성능으로 풀린 사례다.

이 결과를 근거로 무료 모델로 전환했다. 상시 운영 비용이 0원이 되었다.

4.3 전환 과정

바꾸는 것 자체는 환경변수 세 개지만 실제로는 두 번 막혔다. 한 번은 평가 결과가 모델 성능이 아니라 호출 실패를 측정한 것이었고, 한 번은 진단 에이전트가 통째로 죽었다. 둘 다 별지 2에 적었다.

5. 운영 안정성

워커가 멈추면 전체가 멈추던 문제를 고쳤다. 워커가 확장 실행 중에 죽으면 그 작업이 "실행 중" 상태로 영원히 남고, "처리 안 된 작업이 있으면 새 제안 안 함" 규칙과 맞물려 이후 제안이 전부 막혔다. 일정 시간을 넘긴 작업은 실패로 정리하게 했다.

오류 응답에 내부 정보가 나가던 것도 고쳤다. 예외가 나면 스택트레이스가 그대로 응답에 실렸는데, 공통 예외 처리를 붙여 정해진 형식의 메시지만 나가게 했다.

테스트는 백엔드 38개, AI 서비스 120개(탐지 29, 대응 39, 진단 17, 검증 12, 워커 11, 재시도 12)로 늘었다. 코드를 올릴 때마다 자동으로 실행된다.

6. 기준 데이터 축적 결과

실제 사용자가 없어 비어 있던 트래픽·응답시간·자원 사용률 기준 데이터를 시뮬레이터로 채웠다. Elasticsearch에 가짜 로그를 넣는 것이 아니라 실제 백엔드 엔드포인트를 호출해, 백엔드가 진짜로 집계한 값이 로그로 남게 했다. 출퇴근 시간에 요청을 많이 보내고 새벽에는 줄이는 하루 패턴을 흉내 냈고, 평균 8시간마다 5~12분 동안 요청을 10배로 늘리는 이상 상황도 섞었다.

  · 가동 기간: 9월 14일부터 9월 28일까지 14일, 중단 없음
  · 골든시그널 요약 로그: 6,894건
  · 시간대 구간: 48개 전부 채워짐
  · 구간당 표본: 최소 11건, 중앙값 93건, 최대 447건
  · 표본 5건 미만 구간: 0개 (2주 전에는 대부분 부족했다)
  · 주입한 트래픽 급증: 12회
  · 탐지된 이상: 0회

기준 데이터는 목표대로 확보했다. 하지만 급증 12번 중 한 번도 탐지하지 못했고, 이것이 이번 기간의 가장 큰 발견이다.

별지 2. 문제점 및 해결

1. 검증 패널이 진짜 이상을 오탐으로 낮추던 문제

별지 1의 3.1에 적었다. 심사관 역할의 LLM이 "서버 한 대", "데이터 40건"을 근거 부족으로 잘못 보고 있었다. 오탐이라고 판단할 수 있는 이유를 프롬프트에서 명시적으로 제한해 해결했고, 판정 정확도가 80%에서 100%로, 심사관 일치율이 61%에서 92%로 올랐다.

평가 케이스를 만들지 않았으면 못 찾았을 문제다. 만들기 전에는 몇 번 돌려 보고 잘 되는 것 같다고 생각하고 있었다.

2. 진단 에이전트가 원인을 지어내는 문제

원인이 불분명한 케이스에서 "모르겠다"고 하지 않고 억지로 원인을 만들어 냈다. "확신하는지"를 따로 답하게 해서 고치려 했는데, 이번엔 원인이 분명한 케이스까지 모르겠다고 해서 오히려 나빠졌다. 원래대로 되돌렸다.

이후 무료 모델로 바꾸면서 다시 측정했더니 두 건 중 한 건이 해결됐다(결론 적절성 75% → 88%). 프롬프트로 못 고친 것이 모델 성능으로 풀린 셈이다. 남은 한 건(로그가 4건뿐인 케이스)은 여전히 억지로 결론을 낸다. 진단은 판정이나 대응을 바꾸지 않는 설명용 산출물이고 확신도가 함께 표시되므로, 관찰 대상으로 두기로 했다.

3. AI 서비스가 Elasticsearch보다 먼저 떠서 첫 분석이 실패하던 문제

방학이 끝나고 서버를 다시 띄웠을 때 발견했다. AI 서비스는 기동 직후 분석을 한 번 돌리는데, 실행 순서만 지정되어 있고 "준비될 때까지 기다리기"가 없어서 Elasticsearch가 아직 응답하지 못하는 상태에서 호출해 실패했다. 하루 두 번만 돌던 때는 다음 실행이 몇 시간 뒤라 그동안 결과가 비어 있었다.

Elasticsearch에 상태 검사를 추가하고 AI 서비스가 그것을 기다리도록 바꿨다. 전체를 내렸다 올려서 첫 분석이 정상으로 끝나는 것까지 확인했다.

4. 시뮬레이터를 백그라운드로 켜면 잘못된 요청만 보내던 문제

시뮬레이터를 켜 놓고 나가려고 백그라운드로 실행했더니 곧바로 오류가 쏟아졌다. 앞에서 실행할 때는 멀쩡했기 때문에 처음에는 원인을 짐작하지 못했다.

역 목록을 임시 파일에 저장해 두고 매번 그 파일에서 무작위로 한 줄을 뽑는 구조였는데, 백그라운드로 띄우고 실행한 창을 닫으면 그 임시 파일이 정리된다. 그래서 역 번호가 빈 채로 잘못된 주소를 계속 호출하고 있었다. 파일 대신 메모리에 배열로 들고 있도록 고쳤다.

고친 뒤 창을 닫고 관찰했을 때 오류가 없고 백엔드가 요청을 정상으로 받는 것을 확인했다. 결과적으로 14일 동안 오류 한 줄(절전 중 발생한 연결 시간 초과)만 남기고 완주했다.

5. 급증을 12번 주입했는데 한 번도 탐지하지 못한 문제

이번 기간에서 가장 중요한 발견이다.

기준 데이터가 다 찼는데도 탐지가 0건이라 처음에는 탐지 기준이 너무 높은 줄 알았다. 그런데 분석 결과를 세어 보니 14일 동안 분석이 12번밖에 돌지 않았고, 9월 20일 이후로는 한 번도 돌지 않았다. 하루 두 번이면 28번은 돌았어야 한다.

로그에 원인이 있었다. 정해진 시각(오전 8시, 오후 6시)에 실행하는 방식인데, 그 시각에 노트북이 절전 상태면 그 회차를 통째로 건너뛴다. 깨어난 뒤에 밀린 것을 실행하지도 않는다. 로그에는 실행 시각을 17시간 45분 놓쳤다는 경고가 남아 있었다.

설령 전부 실행됐더라도 탐지는 어려웠다. 주입한 급증은 5~12분 동안 지속되는데 분석은 하루 두 번 각 10분 구간만 본다. 우연히 겹칠 확률이 거의 없다.

애초에 하루 두 번으로 줄인 이유는 호출 비용 때문이었다. 그런데 이번에 정상일 때는 LLM을 부르지 않도록 고쳤으므로 그 이유가 사라졌다. 5분 간격 상시 관측으로 되돌렸고, 간격 방식은 절전에서 깨어나면 다음 주기에 바로 복구되므로 정해진 시각 방식처럼 통째로 건너뛰지 않는다. 전환 후 5분마다 정상 실행되는 것을 확인했다.

6. 평가 결과가 모델 성능이 아니라 호출 실패를 측정한 문제

무료 모델로 바꾸고 검증 평가를 처음 돌렸을 때 판정 정확도 50%가 나왔다. 유료 모델은 100%였으니 무료라서 떨어지는구나 하고 결론 내릴 뻔했다.

로그를 보니 평가 도중에 호출이 한도 초과로 계속 실패하고 있었다. 검증 패널은 심사관 호출이 실패하면 그 심사관을 기권 처리하고 통계 판정을 유지하도록 만들어져 있다. 안전한 설계지만, 그래서 오탐 5건이 전부 "강등 안 함"으로 처리되었고 이것이 오답으로 채점된 것이다. 모델이 그렇게 판단한 것이 아니라 호출이 막혀서 판단 자체를 못 한 상태를 성능으로 측정하고 있었다.

원인은 두 가지였다.

첫째, 무료 API는 모델마다 하루 호출 한도가 다른데 처음 고른 최신 모델이 하루 20회 제한이었다. 평가 한 번에 36회가 필요하니 절반도 못 돌린다. 한도가 넉넉한 모델로 바꿔 해결했다.

둘째, 이 시스템은 호출이 몰린다. 검증은 심사관 3명을 연달아 부르고 진단은 최대 6단계를 연달아 부르므로, 이상이 한 번 확정되면 수 초 안에 8~10회가 나간다. 무료 API는 분당 요청 수도 제한하므로 뒷부분이 실패한다. 서버가 알려주는 대기 시간만큼 기다렸다 다시 시도하는 처리를 추가했다.

여기서 한 번 더 헛걸음을 했다. 하루 한도가 소진된 경우에도 서버는 56초 뒤에 다시 시도하라고 알려준다. 그 말을 그대로 믿고 기다리게 했더니 평가 한 번에 30분을 허비했다. 하루 한도는 기다려도 그날 안에는 풀리지 않으므로, 응답에 담긴 한도 종류를 구분해 분당 제한이면 기다리고 하루 한도면 즉시 포기하도록 고쳤다.

평가 점수가 나쁘게 나오면 대상을 의심하기 전에 측정이 제대로 됐는지부터 확인해야 한다는 것을 배웠다.

7. 진단 에이전트가 무료 모델에서 통째로 죽던 문제

모델을 바꾸고 진단 평가를 돌렸더니 8케이스 전부 생략 처리되고 근본원인 정확성 0%가 나왔다. 앞의 사례를 겪은 뒤라 이번에도 측정 문제를 먼저 의심하고 로그를 봤다.

Gemini는 도구 호출 응답에 서명 값을 함께 보내고, 다음 차례에 그 값을 그대로 돌려줘야 대화를 이어 준다. 돌려주지 않으면 2단계째에 거절당한다. 우리 진단 루프는 응답에서 도구 이름과 인자만 꺼내 쓰고 서명은 버리고 있었다.

까다로웠던 점은 1단계 호출은 정상이라는 것이다. 연결 확인용으로 한 번 호출해 보면 도구 호출이 잘 되므로 문제가 없어 보인다. 여러 단계를 도는 평가를 돌려야만 드러난다.

처음에는 서명을 메시지에 담아 보내는 방식으로 고치려 했는데 같은 오류가 다시 났다. 확인해 보니 사용 중인 라이브러리가 도구 호출을 전송하기 직전에 정해진 세 개 항목만 남기고 나머지를 버리고 있었다. 라이브러리로는 보낼 방법이 없었다.

그래서 진단 호출 부분만 라이브러리를 걷어내고 API를 직접 호출하도록 바꿨다. 진단 루프는 원래 평범한 자료 구조로 메시지를 주고받고 있어서 교체 지점이 한 곳뿐이었다. 고친 뒤 8케이스 전부 정상으로 진단했고, 서명을 제대로 돌려주는지 확인하는 테스트 2개를 추가했다.

8. 아직 해결되지 않은 것

  · 노트북 절전. 5분 간격으로 바꿔도 절전 중에는 분석이 돌지 않는다. 발표 전까지 절전을 꺼 두어야 하며, 상시 서버가 없는 구조의 한계다.
  · 서버 줄이기 경로 미검증. 정상 판정이 6번 이어져야 축소를 제안하므로 아직 실제로 돌려 보지 못했다. 리허설에서 확인할 예정이다.
  · 비밀번호가 코드에 그대로 있음. docker-compose 설정에 데이터베이스 비밀번호가 적힌 채 공개 저장소에 올라가 있다. 외부 서버에 올리기 전에 바꿔야 한다.
  · 로그가 희소한 경우의 억지 결론. 진단 에이전트가 근거가 4건뿐인 상황에서도 결론을 낸다. 모델을 바꿔 한 건은 해결됐으나 이 경우는 남았다.
  · 상시 서버 없음. 전시회(11월 9일) 때 어떻게 할지 정해야 한다.
